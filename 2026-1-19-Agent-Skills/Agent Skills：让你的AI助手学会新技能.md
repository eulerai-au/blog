# Agent Skills：让你的AI助手学会新技能
## <h2 align="center">当"聊天"不再够用，AI Agent需要更多技能<h2>
还记得ChatGPT刚问世时的惊艳吗？那个能够流畅对话、回答问题的AI助手让我们看到了人工智能的无限可能。然而，随着技术的发展，我们逐渐发现：仅仅会"聊天"的AI，就像只会一种技能的工具人，能力终究有限。
想象一下这些场景：让AI帮你规划一次完整的旅行，从查询航班、预订酒店到推荐景点、计算预算，实现一站式服务；或是让它分析一份财务报表，自动提取数据、生成图表并撰写分析报告；甚至让它管理你的日程安排，智能协调会议时间、发送提醒、准备会议资料。每一种场景，都代表着AI需要掌握的一项完整"技能"。
而这背后的关键技术，正是我们今天要介绍的**Agent Skills**——一种赋予AI Agent多样化能力的技术方案，让它从单一功能的"聊天工具"真正进化为能够处理复杂任务的"多面手"。

## <h2 align="center">什么是Agent Skills？<h2>
1. **AI的"培训手册"**
    想象一下公司来了新员工，你会怎么做？
    传统做法是口头传授：告诉他怎么使用报销系统、如何预订会议室、找谁申请设备……新员工需要记住大量零散的信息，遇到问题还得反复询问。这就像早期的聊天AI，每次遇到新任务都需要从头学习，效率低下并且容易出错。
    有了培训手册之后，情况完全不同：新员工可以随时查阅标准化的操作流程，每个任务都有清晰的步骤说明。需要报销？翻开手册第三章；要订会议室？看第五章。这种方式不仅高效，而且可复，让每个新员工都能快速上手。
    **Agent Skills正是AI Agent的"培训手册"**。它将各种任务能力标准化、模块化地封装起来，让Agent可以像查阅手册一样，快速调用所需的技能来完成工作。这种设计让AI从"每次都要重新学习"变成了"拿来即用"，大大提升了实用性和可靠性。

2. **Skills与传统Prompt的区别**
    你可能会问：这和我们平时给AI写的Prompt有什么不同？看起来都是用自然语言告诉AI做什么。
    核心差异在于：Skills是将临时指令写成了标准操作手册（SOP）。举个例子：传统方式下，你每次让AI整理会议纪要都要重新描述："提取关键讨论点、列出待办事项、标注负责人、设置截止时间……"而使用Skills，你创建一个"会议纪要整理"SOP，之后只需说"用会议纪要Skill处理这段录音"，Agent就能按标准流程执行。这种设计让复杂任务的自动化成为可能。

3. **谁在使用Skills**？
    2025年10月，Anthropic正式推出Agent Skills系统。这项技术的核心理念非常简单却极其有效：将专业知识和工作流程打包成独立的"技能包"，每个技能包就是一个包含指令文档、脚本和资源的文件夹，AI可以在需要时动态调用。Claude现在已经提供了文档编辑、表格处理、演示文稿制作等预构建技能，用户也可以创建自己的定制技能。
    这个设计的优雅之处立即引起了整个行业的关注。OpenAI在仅仅两个月后的12月就在ChatGPT和Codex工具中加入了Skills支持。Google也快速跟进，Gemini CLI和企业级平台都原生支持Agent Skills标准，并通过Workspace Studio让普通员工用自然语言就能创建自动化agent，目前每月已有超过2000万任务通过这些agent完成。
    更重要的是，Anthropic在12月将Agent Skills发布为开放标准，使得在Claude中创建的技能可以直接用于ChatGPT、Gemini等其他平台。这种跨平台可移植性，加上LangChain、AutoGen等主流开发框架的适配，正在形成一个统一的agentic AI生态系统。从技术实现到产业应用，Agent Skills正在定义AI代理的未来标准。

## <h2 align="center">传统AI的局限<h2>
在Agent Skills出现之前，单一技能的AI（主要是对话能力）虽然看起来强大，但在实际应用中却面临着三个致命问题：上下文窗口有限、复杂任务处理不一致、专业知识无法沉淀。这些问题让AI始终停留在问答阶段，难以真正投入生产环境。

让我们通过几个例子来看看这些问题。

**例子1：上下文窗口导致的“健忘症”** 
这个场景你可能很熟悉
>你：请帮我写一份产品分析报告，标题用二号黑体，正文用小四宋体，要包含市场趋势、用户画像、功能对比……（详细说明了500字的格式要求）
AI：好的！（生成了一份完美的报告）
第二天
你：再写一份竞品分析报告，格式和昨天一样
AI：什么格式？我不记得了 🤷

为什么会这样？因为AI的"记忆"是临时的，依赖于上下文窗口，这就像人的短期记忆，容量有限（比如10万字）。一旦超出这个限制或开启新对话，之前的内容就会被遗忘。这意味着你每次都要重复基础信息，不仅浪费时间，还会消耗更多token（增加成本）。对于需要长期反复的工作场景来说，这简直是灾难。

**例子2：复杂任务的不一致性**
>你让AI处理100个客户反馈，要求分类并生成摘要。结果你会发现：
第一次尝试：AI分了5个类别（功能建议、Bug反馈、体验问题、价格咨询、其他）
第二次尝试：AI分了8个类别（功能改进、新功能请求、技术故障……）
第三次尝试：分类标准又变了，有些反馈被归到了完全不同的类别

问题出在哪？AI每次理解任务的角度可能不同，没有固定的"标准操作流程"。这种随机性在简单对话中还能接受，但处理复杂任务时就成了大问题——你无法确保结果的一致性和可靠性，更不敢把这种不稳定的AI用在生产环境中。

**例子3：专业知识无法沉淀**
下面是一个代码审查的场景：
>第1周：你让AI帮你做代码审查
AI：检查了语法和基本逻辑
你："还要检查安全问题，比如SQL注入"
AI：好的！【加上了安全检查】
第2周：同样的代码审查任务
AI：只检查了语法和基本逻辑（忘记了安全检查）
你：【又要重新提醒一遍安全问题】
第3周：你发现还需要检查性能问题
你：【不仅要说性能，还要重复安全、语法……】
第4周：团队新人接手
新人：【完全不知道前面积累的审查要点，又从零开始】

在人类工作中，我们是这样进步的：Version 1.0检查语法错误 → 发现问题后改进到Version 2.0加入安全检查 → 踩了坑后再升级到Version 3.0加入性能检查 → 持续优化到Version 4.0包含代码风格和测试覆盖率。代码审查清单越来越完善。但AI每次都是从头开始：忘记之前补充的检查项、忘记上次踩过的坑、忘记团队总结的经验。结果就是永远在重复Version 1.0，专业知识无法积累和传承。

这三个问题的根源在于：传统AI缺乏标准化的能力封装机制。Agent Skills的出现，正是为了突破这些限制——通过模块化设计解决上下文问题，通过标准接口实现能力扩展，通过开放生态促进知识共享。

## <h2 align="center">Skill的文件夹结构<h2>
从技术实现上看，一个Agent Skill就是一个结构化的文件夹，就像你电脑里的项目目录一样。让我们打开这个文件夹，看看里面都有什么：

```
pdf/
├── SKILL.md              # 主要指令(技能触发后加载)
├── FORMS.md              # 表单填写指南（按需加载）
├── reference.md          # API参考文档（按需加载）
├── examples.md           # 使用示例（按需加载）
└── scripts/
    ├── analyze_form.py   # 工具脚本（执行，不加载）
    ├── fill_form.py      # 表单填写脚本
    └── validate.py       # 验证脚本
```

* **SKILL.md（必需）**：技能的"说明书"

  这是每个Skill的核心文件，用Markdown格式编写。它包含两部分关键内容：

  1. 技能名称和描述：清晰说明这个技能是做什么的，适用于什么场景

  2. 详细操作指南：用自然语言告诉Agent具体怎么执行任务，包括步骤、注意事项和预期输出

```
---
name: pdf-processing
description: 从PDF文件中提取文本和表格，填写表单，合并文档。当需要处理PDF文件或用户提到PDF、表单或文档提取时使用。
---

# PDF处理

## 快速开始

使用pdfplumber提取文本:
python
	import pdfplumber
	with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()

## 高级功能

**表单填写**: 查看[FORMS.md](FORMS.md)获取完整指南
**API参考**: 查看 [REFERENCE.md](REFERENCE.md)了解所有方法
**示例**: 查看[EXAMPLES.md](EXAMPLES.md)了解常见用法
```

* scripts/（可选）：精确执行的代码

  当任务需要精确的逻辑控制时，可以在这个文件夹中放置Python、JavaScript等脚本。比如复杂的数据处理算法、特定的API调用逻辑等。Agent可以直接调用这些脚本，确保关键步骤的准确性。

* references/（可选）：参考资料和知识库
  存放领域知识、FAQ文档、产品手册等参考资料。Agent执行任务时可以查阅这些内容，让回答更专业、更准确。

* assets/（可选）：模板和资源文件
  包含文档模板、图片素材、配置文件等。例如，一个"生成报告"Skill可能需要预设的Word模板或PPT模板

这种文件夹结构的设计简洁而强大：SKILL.md提供核心指令，其他文件夹按需添加，既保证了标准化，又提供了足够的灵活性。

## <h2 align="center">Skills是如何工作的？<h2>
想象一下，Agent Skills运行在一个虚拟的工作环境中，就像AI有了自己的"电脑"——它可以访问文件系统、执行命令、运行代码。Skills就像这台电脑里的文件夹，AI通过命令来读取和使用它们。
当一个Skill被触发时，AI会像你打开文件一样，读取SKILL.md文件，把里面的指令加载到"工作记忆"中。如果指令提到了其他文件（比如FORMS.md或数据库结构文档），AI会继续读取这些文件。而当遇到可执行脚本时，AI会直接运行它们，只接收脚本的输出结果，脚本代码本身不会占用"记忆空间"。

这种设计有什么好处？

* 按需加载，节省资源：AI只读取当前任务需要的文件。
* 高效执行脚本：脚本代码本身不会被加载，只有运行结果会进入AI的"工作记忆"。
* 内容容量无限制：文件在被访问之前不消耗资源，只要不用，就不会有任何负担。

这种基于文件系统的模式，就是"渐进式披露"（ Progressive Disclosure）的核心。AI像你查阅入门指南的特定章节一样，浏览Skill的文件夹结构，精确访问每个任务所需的内容。这种设计让AI既能掌握海量专业知识，又不会被信息淹没。

**实战案例：看看Skills是如何运转的**
让我们通过一个PDF处理的真实例子，看看Agent Skills从触发到完成任务的完整过程：
* 第一步：系统启动时的"技能目录"
当AI启动时，系统会加载一份简短的"技能目录"，就像图书馆的索引卡片。对于PDF处理技能，目录中只有一行简介：`PDF Processing - 从PDF文件中提取文本和表格，填写表单，合并文档`
* 第二步：用户发出请求
用户说："帮我从这个PDF中提取文本并总结一下内容"
* 第三步：AI识别并加载相关技能
AI扫描技能目录，发现"PDF Processing"技能匹配这个任务。于是它执行命令：`bash: read pdf-skill/SKILL.md`。这时候，SKILL.md文件中的详细指令才被读取并加载到Claude的"工作记忆"中。
* 第四步：智能判断，按需加载
AI阅读SKILL.md后发现，这个任务只需要提取文本功能，不涉及表单填写。于是它跳过了FORMS.md文件——尽管这个文件就在文件夹里，但因为不需要，所以不会被加载，节省了宝贵的"记忆空间"。
* 第五步：执行任务
AI根据SKILL.md中的指令，调用相应的工具和脚本完成PDF文本提取和总结任务。

## <h2 align="center">常见困惑：Skills vs MCP<h2>
在讨论Agent Skills时，很容易产生疑惑：这和MCP（Model Context Protocol，模型上下文协议）有什么区别？它们是竞争关系吗？
答案是：它们不是竞争对手，而是互补的好伙伴。
MCP关注的是"连接"。它就像一套标准化的接口规范，让AI Agent能够方便地连接各种外部系统，例如数据库、API服务、企业应用等。比如你想让AI访问公司的CRM系统、连接Slack、读取Google Drive文档，MCP提供了统一的连接方式。它解决的是"AI如何与外部世界交互"的问题。
Skills关注的是"能力"。它将具体的任务流程、操作指南、领域知识封装成标准化的模块。当你需要AI完成"调研产品"、"分析用户"、"审查代码"这类完整任务时，Skills提供了清晰的执行框架。它解决的是"AI如何完成复杂任务"的问题。
两者可以完美配合：一个"客户数据分析"Skill可能会用到MCP来连接CRM系统获取数据，然后按照Skill中定义的分析流程处理数据，最后生成报告。MCP负责"拿到数据"，Skills负责"知道怎么用这些数据"。
用个比喻来说：MCP是USB接口标准，让设备能够互联互通；Skills是应用程序，定义了具体能做什么事。你的电脑需要USB接口来连接外设，也需要各种软件来完成具体工作——两者缺一不可。

AI会往哪里走？答案已经逐渐显现：更专业、更可靠、更好用。而Agent Skills，就是通往这个未来的关键一步。
